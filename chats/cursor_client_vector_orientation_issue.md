**Cursor**

Уточняю порядок вершин bbox у Yandex OCR и место, где он мапится на углы фрагмента.

В официальном примере Yandex порядок вершин другой, чем ожидает warp — проверяю это и обновляю план.

Нашёл конкретное несоответствие: в примере Yandex OCR порядок `TL→BL→BR→TR`, а `WarpPerspective` ожидает `TL→TR→BR→BL`. Обновляю план.

Конкретное место ошибки — [`WordFragmentExtractor.WarpPerspective`](handwritingOCR.Server/Imaging/WordFragmentExtractor.cs): углы фрагмента жёстко считаются как **TL → TR → BR → BL**, а Yandex отдаёт другой порядок.

**Как приходят координаты от Yandex OCR**

[`YandexOcrService.ParseBoundingBox`](handwritingOCR.Server/Services/YandexOcrService.cs) просто копирует `vertices[0..3]` → `X1..Y4` без перестановки.

В официальном примере handwritten OCR для `"Hello"`:

| index | coords | угол |
|------:|--------|------|
| 0 | (28, 9) | TL |
| 1 | (28, 81) | **BL** |
| 2 | (240, 81) | BR |
| 3 | (240, 9) | **TR** |

Порядок Yandex: **TL → BL → BR → TR** (сначала вниз по левому краю).

**Что делает код**

`WarpPerspective` мапит:

- `X2,Y2` (фактически BL) → верхний правый угол фрагмента  
- `X4,Y4` (фактически TR) → нижний левый  

Плюс `outW`/`outH` берут ребро `0→1` за ширину, хотя у Yandex это высота слова → фрагмент ещё и «переворачивается» по осям.

Рамки на скане выглядят нормально, потому что для `<polygon>` обход не важен; для гомографии — критичен.

План обновлён: перед warp переставлять `[0,1,2,3]` → `[0,3,2,1]` (TL,TR,BR,BL), не трогая X1..Y4 в БД.
