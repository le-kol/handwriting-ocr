# Research: Отображение и векторизация слов на клиенте

**Feature**: `002-words-vector-ui`  
**Date**: 2026-08-11

## 1. Рендер миниатюры: SVG vs Canvas

**Decision**: Рисовать миниатюру через **SVG** (`<path>` с командами кубической Безье `C` / `M`), с `viewBox`, выставленным по bounding box всех контрольных точек кривых слова (плюс небольшой padding в единицах координат фрагмента).

**Rationale**:
- На экране уже используется SVG для рамок слов поверх скана — тот же стек, без новых зависимостей.
- `viewBox` естественно задаёт собственную СК превью и масштабирует форму в фиксированный viewport ячейки таблицы.
- Декларативный React-рендер проще сопровождать, чем imperative Canvas redraw.

**Alternatives considered**:
- **Canvas 2D** (`bezierCurveTo`): гибко, но больше кода жизненного цикла и сложнее отлаживать в DOM; нет выигрыша для статичной миниатюры.
- **Наложение path на изображение скана**: прямо запрещено spec (координаты фрагмента ≠ координаты скана).

## 2. Система координат и bounding box

**Decision**: Миниатюра использует **только** координаты `curvePoints` (СК выровненного фрагмента из 001). Bounding box = min/max по всем контрольным точкам всех кривых; при нулевой ширине/высоте — минимальный ненулевой размер (или заглушка), чтобы `viewBox` не вырождался. Небольшой padding (~5% от max(width,height) или фиксированные 2–4 единицы) — чтобы штрихи не обрезались краем.

**Rationale**: Соответствует Assumptions/ADR 001 и FR-005/FR-006; оператор видит форму, а не ложное совпадение с рамкой на скане.

**Alternatives considered**:
- Использовать размер фрагмента с сервера — сервер размер фрагмента в JSON слова не отдаёт; bbox по точкам достаточен.
- Масштаб 1:1 пиксель фрагмента без fit — миниатюры разного размера плохо читаются в таблице.

## 3. Формат `curvePoints` на клиенте

**Decision**: Расширить интерфейс `Word` опциональным полем:

```ts
curvePoints?: number[][][] | null; // [curve][point 0..3][x|y]
```

Считать слово **векторизованным**, если `Array.isArray(curvePoints) && curvePoints.length > 0`. Перед рисованием валидировать каждую кривую: ровно 4 точки, у каждой 2 конечных числа; невалидные кривые пропускать; если после фильтра пусто — не рисовать миниатюру (без падения UI).

**Rationale**: Зеркалирует серверный camelCase JSON (конституция Client–API Contract); пустой массив на сервере не хранится, но клиент защищается от битых данных (edge case из spec).

**Alternatives considered**:
- Typed arrays / отдельный DTO — избыточно для одного экрана.
- Игнорировать валидацию — риск runtime при ручной порче данных.

## 4. Размещение UI: таблица рядом со сканом

**Decision**: Добавить на основной экран (`App.tsx`) секцию **«Слова скана»** в виде HTML-таблицы (или семантического списка с колонками): Текст | Статус | Миниатюра | Действие. Секция видна, когда выбран `scanId` и слова загружены (в т.ч. после recognize / повторного `fetchWords`). Существующий редактор выбранного слова и SVG-оверлей скана **не** используют координаты миниатюры.

**Rationale**: Spec допускает список или таблицу; таблица даёт явные колонки под FR-002…007. Один экран — без роутинга (конституция: один основной экран).

**Alternatives considered**:
- Встроить статус только в текущий layout по строкам OCR — хуже для миниатюр и кнопки на каждое слово.
- Отдельная страница — вне текущего UX и без нужды.

## 5. Загрузка слов и обновление после vectorize

**Decision**:
- Источник списка — уже существующий `GET /api/Scans/{id}/words` (`fetchWords`); расширить разбор JSON полем `curvePoints` (сервер уже отдаёт).
- `POST /api/Scans/{id}/words/{wordId}/vectorize` без тела; при `ok` — JSON слова; при ошибке — `await response.text()`.
- После успеха: **точечно заменить** слово в массиве `words` (и при необходимости в `layoutLines` тот же объект/поля) данными ответа; полный refetch допустим как fallback, но точечный update быстрее и не сбрасывает UI-состояние редактора без нужды.
- Пока запрос идёт: хранить `vectorizingWordId` (или Set id); кнопка этого слова `disabled`.
- При ошибке: показать статус/сообщение рядом со строкой или общим статус-блоком; **не** обнулять `curvePoints` в state.

**Rationale**: Контракт 001 уже возвращает полное слово с `curvePoints`; карта ошибок — plain text. FR-008…010 закрываются без новых endpoint'ов.

**Alternatives considered**:
- Всегда полный `fetchWords` после vectorize — проще, но лишний round-trip и риск мигания; оставить как запасной путь при необходимости синхронизации layout.
- Оптимистичный UI до ответа — риск рассинхрона при 400/404.

## 6. Кнопка для несохранённых слов (`id === 0`)

**Decision**: Для черновика с `id === 0` кнопку «Векторизовать» **не показывать** или держать disabled (векторизация требует Id в БД).

**Rationale**: Endpoint требует `wordId`; конституция: новое слово — черновик до `POST …/words`.

## 7. Backend / схема

**Decision**: **Не менять** сервер, Liquibase, опции векторизации. Зависимость: фича 001 уже задеплоена/собрана в рабочей ветке.

**Rationale**: Spec явно опирается на существующие GET/POST; объём — UI.
