# Feature Specification: Удаление скана

**Feature Branch**: `006-delete-scan`

**Created**: 2026-08-14

**Status**: Draft

**Input**: User description: "Добавить удаление скана: кнопку и backend endpoint. Подтверждение перед удалением не требуется — удаление происходит сразу по клику. Backend: DELETE /api/Scans/{id} — удаляет запись скана из БД (слова удаляются каскадно существующим ON DELETE CASCADE, отдельно ничего не удалять) и файл изображения с диска через существующий FileStorageService. Успех — 204 NoContent. Скан не найден — 404 «Не найдена запись в БД». Если файл на диске уже отсутствует к моменту удаления — это не считается ошибкой всего запроса (запись в БД и так удаляется), но такой случай не должен приводить к 500. Frontend — два места вызова одного и того же действия: 1) кнопка «Удалить скан» в панели действий текущего открытого скана; 2) кнопка «Удалить» в каждой строке таблицы сканов. Не входит в объём: подтверждение удаления; массовое удаление; восстановление (undo)."

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Удаление текущего открытого скана из редактора (Priority: P1)

Оператор работает с документом в редакторе и решает удалить его полностью из системы. В панели действий рядом с «Распознать текст» и «Добавить слово» есть кнопка «Удалить скан». Один клик — без дополнительного подтверждения — удаляет текущий скан. После успеха редактор возвращается в пустое состояние: как до выбора или загрузки скана (нет текущего идентификатора, слов, раскладки, черновика и статусов операций).

**Why this priority**: Основной сценарий очистки после завершения работы или ошибочной загрузки; оператор не должен искать скан в таблице, если он уже открыт.

**Independent Test**: Открыть скан с распознанными словами и черновиком правки, нажать «Удалить скан»; скан исчезает из хранилища, редактор пуст, повторное открытие по id невозможно.

**Acceptance Scenarios**:

1. **Given** в редакторе открыт скан с идентификатором, словами и/или черновиком, **When** оператор нажимает «Удалить скан», **Then** система удаляет запись скана и связанные слова, удаляет файл изображения с диска, возвращает успех без тела ответа, редактор сбрасывается в пустое состояние.
2. **Given** в редакторе не выбран скан (пустое состояние), **When** оператор смотрит на панель действий, **Then** кнопка «Удалить скан» недоступна или отсутствует — удалить «ничего» нельзя.
3. **Given** удаление текущего скана завершилось ошибкой (сеть, сервер), **When** оператор видит сообщение об ошибке, **Then** скан остаётся открытым в редакторе, состояние редактора не сбрасывается.
4. **Given** запись скана уже удалена другим действием, **When** оператор нажимает «Удалить скан» для несуществующего id, **Then** система отвечает «не найдено» с текстом «Не найдена запись в БД»; клиент показывает ошибку, редактор не переходит в «успешно удалён» без фактического успеха.

### User Story 2 - Удаление скана из строки таблицы (Priority: P1)

Оператор просматривает таблицу сканов и удаляет ненужный документ прямо из строки, не открывая его в редакторе. В каждой строке есть кнопка «Удалить». Клик сразу инициирует удаление этого скана. После успеха таблица обновляется: повторно запрашивается текущая страница списка. Если после удаления страница оказалась пустой и это не первая страница — клиент переходит на предыдущую страницу и показывает её.

**Why this priority**: Таблица — основной способ обзора всех сканов; удаление из строки избавляет от лишнего шага «открыть → удалить».

**Independent Test**: Иметь несколько сканов на второй странице таблицы, удалить один из строки; строка исчезает, список актуален. Удалить последний скан на второй странице — показывается первая страница.

**Acceptance Scenarios**:

1. **Given** в таблице отображается строка скана, **When** оператор нажимает «Удалить» в этой строке, **Then** скан удаляется из хранилища, строка исчезает после обновления списка, остальные строки страницы остаются корректными.
2. **Given** удаляемый скан не открыт в редакторе, **When** удаление успешно, **Then** состояние редактора (текущий скан, слова, черновик) не меняется.
3. **Given** удаляемый скан совпадает с текущим открытым в редакторе, **When** удаление из таблицы успешно, **Then** применяется тот же полный сброс редактора, что и при удалении из панели действий (пустое состояние).
4. **Given** оператор на странице N (N > 1) и на ней один скан, **When** этот скан удалён, **Then** таблица показывает страницу N − 1 с актуальным списком, а не пустую страницу N.
5. **Given** удаление из строки завершилось ошибкой, **When** оператор видит сообщение, **Then** строка остаётся в таблице, редактор не сбрасывается без успешного удаления.

### User Story 3 - Надёжное серверное удаление с учётом целостности данных (Priority: P1)

Система обеспечивает атомарное с точки зрения домена удаление скана: запись в базе и файл изображения. Слова скана исчезают вместе с записью скана за счёт уже существующего каскадного удаления — отдельно удалять слова не требуется. Если файл на диске уже отсутствует, операция всё равно считается успешной для клиента после удаления записи в базе; такая ситуация не должна приводить к внутренней ошибке сервера.

**Why this priority**: Без корректного backend обе кнопки клиента бессмысленны; устойчивость к «осиротевшим» записям важна для brownfield-данных.

**Independent Test**: Вызвать удаление для существующего скана — 204, записи и файла нет. Вызвать для id без записи — 404 с текстом «Не найдена запись в БД». Имитировать отсутствие файла при наличии записи — 204, запись удалена.

**Acceptance Scenarios**:

1. **Given** скан с идентификатором существует в базе и файл есть на диске, **When** поступает запрос на удаление по этому идентификатору, **Then** ответ без тела (успешное удаление), записи скана и всех его слов в базе нет, файла изображения на диске нет.
2. **Given** скана с указанным идентификатором нет в базе, **When** поступает запрос на удаление, **Then** ответ «не найдено» с телом «Не найдена запись в БД» (plain text).
3. **Given** запись скана есть, но файл изображения на диске уже отсутствует, **When** поступает запрос на удаление, **Then** запись и слова удаляются, ответ — успешное удаление без тела; внутренняя ошибка сервера (500) не возвращается из‑за отсутствия файла.
4. **Given** успешное удаление, **When** клиент повторно запрашивает этот скан (изображение, слова, миниатюру), **Then** система сообщает, что запись не найдена, в том же духе, что и для других операций со сканом.

---

### Edge Cases

- Удаление единственного скана в системе: таблица пуста, редактор пуст, первая страница с `totalCount` 0.
- Удаление последнего скана на последней странице (не первой): переход на предыдущую страницу, не пустой «хвост».
- Два быстрых клика «Удалить» по одному скану: второй запрос — 404 «Не найдена запись в БД»; клиент не должен «ломать» UI.
- Удаление из таблицы, пока открыт другой скан: редактор продолжает показывать другой скан; выделение строки текущего скана в таблице без изменений (если он на странице).
- Удаление открытого скана из таблицы: выделение текущей строки исчезает после сброса редактора.
- Сбой сети при удалении: текстовое сообщение на русском (тело ответа сервера или сообщение о сети); данные на экране не меняются так, будто удаление прошло.
- Скан без слов: удаляется так же, как скан с распознанными словами.
- Скан с несохранённым черновиком слова (`id === 0`): удаление скана уничтожает всё локальное состояние редактора без отдельного сохранения черновика.

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: Система MUST предоставлять операцию удаления скана по идентификатору: `DELETE /api/Scans/{id}`.
- **FR-002**: При успешном удалении система MUST вернуть ответ без тела (HTTP 204 No Content) в соответствии с принятой картой ошибок проекта для удаления.
- **FR-003**: Если запись скана с указанным идентификатором не найдена, система MUST вернуть 404 Not Found с plain-text телом «Не найдена запись в БД».
- **FR-004**: При удалении система MUST удалить запись скана из базы данных. Все слова этого скана MUST удаляться автоматически существующим каскадным правилом связи — отдельные запросы на удаление слов выполнять MUST NOT.
- **FR-005**: При удалении система MUST удалить файл изображения скана с диска средством хранения файлов, уже используемым в проекте для сканов.
- **FR-006**: Если файл изображения к моменту удаления уже отсутствует на диске, система MUST всё равно удалить запись скана в базе и MUST вернуть успешное удаление (204). Такой случай MUST NOT приводить к ответу 500 Internal Server Error только из‑за отсутствия файла.
- **FR-007**: Клиент MUST показывать кнопку «Удалить скан» в панели действий редактора рядом с «Распознать текст» и «Добавить слово». Кнопка MUST удалять текущий открытый скан (его идентификатор). Диалог подтверждения перед удалением MUST NOT показываться.
- **FR-008**: После успешного удаления текущего скана из панели действий клиент MUST полностью сбросить состояние редактора до пустого: очистить идентификатор скана, список слов, раскладку строк, черновик правки и все статусы операций — эквивалент состояния до выбора или загрузки скана.
- **FR-009**: Клиент MUST показывать кнопку «Удалить» в каждой строке таблицы сканов. Кнопка MUST удалять скан этой строки независимо от того, открыт ли он в редакторе. Подтверждение MUST NOT требоваться.
- **FR-010**: После успешного удаления из строки таблицы клиент MUST повторно запросить текущую страницу списка сканов. Если страница стала пустой и её номер больше 1, клиент MUST перейти на предыдущую страницу и загрузить её.
- **FR-011**: Если удалённый из таблицы скан совпадает с текущим открытым в редакторе, клиент MUST применить тот же сброс редактора, что описан в FR-008.
- **FR-012**: Если удалённый из таблицы скан не совпадает с текущим открытым, клиент MUST NOT изменять состояние редактора.
- **FR-013**: При ошибке удаления (сеть или неуспешный ответ сервера) клиент MUST показать понятное текстовое сообщение на русском (`response.text()` при ошибке сервера). Состояние редактора и таблицы MUST NOT обновляться так, будто удаление прошло успешно.
- **FR-014**: Обе точки вызова на клиенте (панель редактора и строка таблицы) MUST использовать одну и ту же операцию удаления на сервере — без дублирования разной логики удаления.
- **FR-015**: Фича MUST NOT включать: диалог подтверждения перед удалением; массовое удаление нескольких сканов за одно действие; восстановление удалённого скана (undo); изменение схемы базы данных (кроме использования уже существующего каскада).

### Key Entities

- **Скан**: Сохранённый документ — запись в базе и файл изображения на диске; владеет набором слов. При удалении исчезает полностью из системы.
- **Слово**: Элемент распознанного или добавленного текста, привязанный к скану; удаляется каскадно вместе со сканом.
- **Таблица сканов**: Постраничный список сканов на основном экране; после удаления строки список MUST отражать актуальное состояние хранилища.
- **Редактор скана**: Основной экран работы с выбранным документом; после удаления текущего скана возвращается в пустое состояние.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: Оператор может удалить открытый скан одним кликом по «Удалить скан» без дополнительных шагов подтверждения; после успеха редактор в 100% случаев находится в пустом состоянии.
- **SC-002**: Оператор может удалить любой скан из таблицы одним кликом по «Удалить» в строке; после успеха удалённый скан не отображается при полном просмотре всех страниц списка.
- **SC-003**: В 100% успешных удалений повторный доступ к тому же идентификатору скана (изображение, слова, миниатюра) возвращает «запись не найдена», а не данные удалённого документа.
- **SC-004**: В 100% случаев, когда файл изображения уже отсутствует на диске, но запись скана ещё есть, операция удаления завершается успехом для клиента, а запись в базе исчезает.
- **SC-005**: При удалении последнего скана на странице N > 1 оператор в 100% случаев видит предыдущую страницу с корректным списком, а не пустую страницу.
- **SC-006**: При ошибке удаления оператор всегда видит текстовое сообщение; открытый скан и строки таблицы не исчезают «молча» без успешного ответа сервера.
- **SC-007**: Не менее 90% участников короткой проверки подтверждают, что могут убрать ненужный скан из системы менее чем за 10 секунд через редактор или таблицу.

## Assumptions

- Каскадное удаление слов при удалении скана уже настроено в схеме базы (`ON DELETE CASCADE`); новые миграции Liquibase для этой фичи не требуются.
- Средство хранения файлов сканов в проекте будет использовано или расширено для удаления файла по сохранённому пути; отдельный новый механизм хранения не вводится.
- Порядок операций на сервере: один `DELETE FROM scans WHERE id = @id RETURNING path` (слова каскадом), затем удаление файла по возвращённому `path`; отсутствие файла на диске не блокирует 204 (FR-006).
- Полный сброс редактора при удалении текущего скана: хелпер `clearToEmptyState()` — `scanId`, `selectedFile`, `uploadStatus`, сброс file input, затем расширенный `resetEditorState()`; переключение строки таблицы по-прежнему использует только `resetEditorState()` + `setScanId`.
- Кнопка «Удалить скан» в редакторе недоступна или скрыта, когда скан не выбран (нет идентификатора).
- Клик по кнопке «Удалить» в строке таблицы не должен одновременно открывать скан в редакторе (событие не всплывает на выбор строки).
- Обновление таблицы после удаления использует существующий постраничный список сканов (фича `005-scans-table-thumbnails`); после удаления клиент остаётся на текущей странице, кроме случая пустой страницы N > 1 из FR-010.
- Сообщения об ошибках следуют принятой карте HTTP проекта: plain text на русском, без JSON ProblemDetails.
- Вне объёма, явно: подтверждение удаления; массовое удаление; восстановление удалённого скана.
