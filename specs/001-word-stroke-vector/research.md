# Research: Векторизация штрихов слова

**Feature**: `001-word-stroke-vector`  
**Date**: 2026-08-11

Все пункты Technical Context закрыты; NEEDS CLARIFICATION не осталось.

## 1. Библиотека обработки изображений

**Decision**: SixLabors.ImageSharp (+ SixLabors.ImageSharp.Drawing при необходимости) для декодирования PNG/JPEG и доступа к пикселям; перспективная вырезка четырёхугольника и скелетизация — собственный код на базе буфера пикселей.

**Rationale**: В csproj сейчас только Npgsql и Swashbuckle; нужна managed-зависимость без нативных runtime-пакетов OpenCV. ImageSharp поддерживает PNG/JPEG, хорошо стыкуется с `byte[]` из `FileStorageService`, кроссплатформенна под `net8.0`.

**Alternatives considered**:
- **OpenCvSharp4** — готовые `warpPerspective` и морфология; отвергнуто из‑за нативных бинарников и усложнения деплоя монолита.
- **System.Drawing.Common** — ограниченная поддержка вне Windows, нежелателен для нового кода на .NET 8.
- **SkiaSharp** — сильнее в отрисовке, слабее как CV-pipeline для скелета.

## 2. Pipeline геометрического представления

**Decision**: Фиксированный offline-pipeline без stroke order:

1. Загрузить изображение скана.
2. PRE-check рамки и пересечения с изображением (см. §2a); затем расширить четырёхугольник X1..Y4 настраиваемым отступом и клипнуть по границам изображения (у края скана отступ с одной стороны может стать меньше — это норма, не ошибка). Проверки итогового размера фрагмента после клипа **нет**.
3. Выполнить перспективное (гомографическое) выравнивание в прямоугольный фрагмент; координаты результата — в системе фрагмента (0..width, 0..height).
4. Градации серого → адаптивная/глобальная бинаризация (чернила = foreground).
5. Скелетизация (Zhang–Suen или эквивалент) → осевые линии.
6. Трассировка связных полилиний скелета.
7. Аппроксимация полилиний кубическими кривыми Безье с порогом погрешности из конфигурации (итеративное разбиение / fit cubic, пока max deviation > tolerance).
8. Если кривых 0 — ошибка, без записи в БД.

**Rationale**: Соответствует spec (геометрия формы, кубические Безье, 4 точки на кривую, порядок кривых не нормируется). Классический подход для offline handwriting vectorization без temporal данных.

**Alternatives considered**:
- Potrace / внешние CLI — лишняя интеграция процессов, хуже для API in-process.
- Контурная (outline) векторизация вместо medial axis — хуже для будущей синтеза «перовой» линии; spec требует осевые линии штрихов.
- ML-модели stroke recovery — вне scope и конституционного стека.
- Post-crop reject по `MinFragmentSidePx` / «пустой фрагмент после клипа отступа» — отвергнуто: ложно бракует валидные слова у края скана, где отступ просто клипается.

## 2a. Критерии рамки до вырезки (без post-crop size check)

**Decision**: Две независимые проверки **до** применения отступа; обе → `ArgumentException` (HTTP 400), разные русские сообщения; запись в БД не выполняется.

1. **Вырожденность самой рамки X1..Y4** (без padding, без учёта границ изображения): площадь четырёхугольника (абсолютное значение формулы шнурка) < `1.0` px² **или** длина любой стороны < `1.0` px → сообщение вроде «вырожденная рамка слова».
2. **Пересечение исходной рамки с изображением** `[0..width] × [0..height]` (снова без padding): если пересечение пустое или площадь пересечения < `1.0` px² → сообщение вроде «рамка слова не пересекается с изображением скана» (не путать с п.1). Это признак рассинхрона данных с файлом (например, скан на диске заменён другим размером), а не «слово у края».

После успешного прохождения п.1–2: применить `PaddingPx`, клипнуть расширенный четырёхугольник по границам изображения и продолжить pipeline. Уменьшение отступа у края — ожидаемое поведение. **Не** браковать результат из‑за ширины/высоты фрагмента после клипа (никакого `MinFragmentSidePx` и аналогов).

**Rationale**: Порог 1 px отсекает нулевую геометрию и полностью «уехавшие» рамки; слова у края остаются валидными при клипе padding.

**Alternatives considered**:
- Единая ошибка «пустой фрагмент после clip» — смешивает край скана с рассинхроном файла; отвергнуто.
- Конфигурируемый `MinFragmentSidePx` после отступа — ложные отказы у края; отвергнуто.

## 3. Хранение `real[]` как трёхмерного массива

**Decision**: Колонка `curve_points real[]` nullable. Логическая форма: `N × 4 × 2` (N кривых, 4 контрольные точки, x/y). Канонический C#-тип — `float[,,]?` (прямоугольный многомерный массив): он напрямую передаётся в Npgsql-параметр многомерного массива PostgreSQL (`NpgsqlDbType.Array | NpgsqlDbType.Real`) без ручной упаковки на стороне БД.

Для HTTP-ответа (`GET .../words`, `POST .../vectorize`) `float[,,]` не сериализуется `System.Text.Json` автоматически (`NotSupportedException` на многомерных массивах) — используется явный `JsonConverter<float[,,]>` (`Float3DJsonConverter`), сериализующий значение во вложенный JSON-массив `[[[x,y],...],...]`, зарегистрированный один раз в `Program.cs`. Внутреннее представление в модели, сервисе и БД остаётся `float[,,]?` без изменений; конвертер работает прозрачно для всех действий, возвращающих `Word` (включая существующий `GetWords`), а не только для нового эндпоинта векторизации.

**Rationale**: Явное требование spec/FR-010..012; PostgreSQL поддерживает многомерные массивы; Npgsql умеет передавать многомерные CLR-массивы.

**Alternatives considered**:
- Отдельная таблица `word_curves` — отвергнуто архитектурным решением в spec.
- `jsonb` — отвергнуто (тип зафиксирован как `real[]`).
- Плоский `real[]` длины `N*8` без размерностей — хуже документирует контракт; при возможности сохранять именно 3D-массив в PG.
- `float[][][]?` (jagged array) — проще сериализуется в JSON «из коробки», но Npgsql умеет передавать многомерные массивы только как прямоугольные CLR-массивы (`T[,,]`), не как jagged `T[][][]` — конвертация в `float[,,]` перед записью в БД потребуется в любом случае, просто переносится в другое место кода. Отклонено — не даёт выигрыша, добавляет двойное представление одних данных.

## 4. Форма HTTP API

**Decision**: `POST /api/Scans/{id}/words/{wordId}/vectorize` без тела (параметры — из конфигурации). Успех: `200 OK` + JSON слова (включая `curvePoints`). Ошибки — plain text.

**Rationale**: Существующие мутации слов всегда scoped к скану (`/{id}/words/{wordId}`); конституция требует следовать путям сканов. Word Id глобально уникален, но проверка принадлежности скану сохраняет инварианты контроллера.

**Alternatives considered**:
- `POST /api/Words/{wordId}/vectorize` — новый контроллер, расходится с текущим стилем.
- Параметры отступа/tolerance в query — отвергнуто FR-015 (конфиг приложения).

## 5. Карта ошибок (маппинг)

**Decision**:

| Ситуация | Сигнал сервиса | HTTP |
|----------|----------------|------|
| Слово не найдено / не принадлежит скану | `null` / false | 404 «Слово не найдено» |
| Скан не найден | путь `null` | 404 «Не найдена запись в БД» |
| Файл отсутствует / не читается | `null` bytes / IO | 404 «Не найден файл» (как GetImage) или 400 при повреждённом содержимом |
| Вырожденная рамка (п.1 §2a) | `ArgumentException` | 400 + RU текст («вырожденная рамка…») |
| Рамка не пересекается с изображением (п.2 §2a) | `ArgumentException` | 400 + RU текст («рамка слова не пересекается…») |
| 0 штрихов / кривых после fitter | `ArgumentException` | 400 + RU текст |
| Не задана/невалидна секция `WordVectorization` | `InvalidOperationException` | 503 |

Повторная векторизация: `UPDATE` только при успехе → при ошибке старое `curve_points` не меняется.

**Rationale**: Принцип III конституции + сценарии User Story 3.

## 6. Конфигурация

**Decision**: Секция `WordVectorization` в `appsettings.json`:

```json
"WordVectorization": {
  "PaddingPx": 4,
  "ApproximationTolerance": 1.5
}
```

- `PaddingPx` ≥ 0 — отступ в пикселях изображения скана.
- `ApproximationTolerance` > 0 — макс. отклонение аппроксимации в пикселях фрагмента.

Bind через `IOptions<WordVectorizationOptions>`; невалидные значения → 503 при вызове (или отказ старта — достаточно fail-on-use по аналогии с OCR).

**Rationale**: FR-003, FR-007, FR-015; разумные дефолты закрывают assumption spec.

## 7. Разбиение сервисов

**Decision**:
- `WordVectorizationService` (scoped) — оркестрация: загрузить слово и путь скана → байты файла → extract → fit → `WordDbService.UpdateCurvePointsAsync`.
- `WordDbService` — `GetWordAsync(scanId, wordId)`, чтение/запись `curve_points` в существующих SELECT/UPDATE; явная транзакция на UPDATE.
- Imaging-хелперы — без DI HTTP; могут быть injected или создаваться сервисом.

**Rationale**: Принцип II; контроллер не знает SQL/CV.

## 8. Клиент (React)

**Decision**: Вне обязательного объёма. `curvePoints` MAY появиться в JSON `GET …/words` после расширения модели; UI кнопки «Векторизовать» не требуется для закрытия фичи.

**Rationale**: Assumptions spec.
